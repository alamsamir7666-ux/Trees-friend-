# Summary — KB Cache Staleness Fix (BUG-1 + BUG-2)

## Problem

Two interconnected CRITICAL bugs caused the TreeBot AI chat assistant to
serve stale (wrong) answers for up to **1 hour** after a Knowledge Base
(KB) admin edit:

- **BUG-1**: KB mutation routes (`/api/ai/admin/kb/*`) never invalidated
  the AI chat caches. The cache-clearing functions existed but were dead
  code in the KB context — only the product/seller-listing routes were
  wired to `invalidateCatalogCache()`.
- **BUG-2**: The Redis cache key was derived from
  `sha256(systemPrompt.slice(0, 500))`, but the dynamic blocks
  (`{{summary}}`, `{{knowledge}}`, `{{catalog}}`, `{{tone}}`) appear
  AFTER char 500 in the prompt template. So two prompts with completely
  different KB context produced the SAME cache key — defeating BUG-1's
  invalidation wiring for the auto-inject path.

## Architecture Decisions

1. **Cache-Aside with Write-Through Invalidation** — every KB mutation
   fires `invalidateKbCache(reason)` AFTER the DB write commits,
   fire-and-forget with `.catch()` for logging. The user-facing
   mutation response is never blocked by cache invalidation.
2. **Content-Addressable Cache Key** — the cache key now uses
   `sha256(fullSystemPrompt)` (Anthropic prompt-cache pattern), so any
   change to the dynamic blocks (including KB context) produces a
   different key.
3. **Best-Effort, Fail-Safe** — three invalidation layers (Redis,
   pgvector, reranker) run in parallel via `Promise.allSettled`. A
   Redis outage doesn't block pgvector clear and vice versa. TTL
   remains a defense-in-depth measure (1h max staleness floor).
4. **What is NOT cleared** — `queryEmbeddingCache` (query embeddings
   are deterministic per query, doc-independent) and
   `ai_kb_entries.embedding` (regenerated by the background
   `kbEmbeddingJob`).
